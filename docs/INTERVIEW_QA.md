# 面试问答清单

> 30 个高频追问 + 标准答法。
> 答法原则：**先给结论 → 再说为什么 → 最后说取舍/踩坑**。面试官想听的是判断力，不是背诵。

---

## A. 方案选型

### Q1: 为什么不用现成的上传组件（ant-design / element-plus upload）？

> 这些组件解决的是「上传交互」，不是「大文件传输」。默认实现是 `FormData` 一次性发送整个文件，2GB 文件浏览器直接 OOM。分片、秒传、断点续传、并发控制都不在组件职责范围内。
>
> 我用的 `el-upload` 只负责「拖拽 + 选文件」，`auto-upload` 设为 false，拿到 `File` 对象后完全由自己的引擎接管。

### Q2: 为什么不直接传到对象存储（OSS / S3）？

> 对象存储确实更适合大文件——支持分片直传（Multipart Upload）和预签名 URL，能绕过应用服务器。
>
> 选当前方案的原因：
> 1. **业务需求**：文件按用户隔离（ownerId），要在服务端管理元数据、做秒传判断，走对象存储还要额外同步；
> 2. **可控性**：合并、原子替换、归属校验自己实现，出问题能快速定位；
> 3. **成本**：小项目没必要引入云存储依赖。
>
> 生产级方案我会改成：**前端直传 OSS（预签名 URL）+ 应用服务器只负责元数据和秒传校验**，分片流量不经过应用服务器。

### Q3: 为什么用 SHA-256 而不是 MD5 / 纯文件名？

> **不用纯文件名**：同名不同内容会被误判成同一文件，秒传变成「覆盖用户文件」，是数据事故。
>
> **用 SHA-256 而不是 MD5**：MD5 已被证明有实际碰撞攻击（2004 年王小云团队）。秒传场景下碰撞意味着「不同文件被认定为同一文件」，用户上传 A 得到 B，是安全问题。
>
> **为什么还拼文件名和大小**：
> - 拼大小：成本几乎为零；
> - 拼文件名：让「同内容不同名」视为两个文件，符合用户直觉。
>
> **代价**：SHA-256 比 MD5 慢约 40%。但只在**首次上传**算一次，续传复用缓存，可接受。

### Q4: 10GB 文件算哈希要多久？怎么优化？

> 纯 JS 约 **100~200 MB/s**，10GB 需要 **50~100 秒**。
>
> 优化手段，按性价比排序：
> 1. **抽样哈希**：只取文件头 2MB + 中段 2MB + 尾 2MB + 大小 做摘要。有极小概率误判，实际可接受，B 站、百度网盘都用这个思路；
> 2. **WASM 实现**：`hash-wasm` 能跑满内存带宽，500MB/s~1GB/s，10GB 降到 10~20 秒；
> 3. **多 Worker 并行**：SHA-256 是链式的，不能简单拆段并行。可行做法是「分块各算 SHA-256 再对结果算一次」，但改了算法语义，秒传 key 就变了；
> 4. **`crypto.subtle.digest` 走原生**：快 2~3 倍，但要求整个文件在内存里，只适合小文件。
>
> 当前取舍：**正确性和内存恒定优先**，速度优化列为 TODO。

## B. 哈希与流式处理

### Q5: 讲讲 SHA-256 的 padding

> SHA-256 一次处理 64 字节（512 bit）的块。消息长度通常不是 64 的整数倍，末尾要补：
> 1. 一个 `0x80` 字节；
> 2. 若干个 `0x00`；
> 3. **8 字节的原始消息比特长度**（大端）。
>
> 使总长度是 64 的整数倍。
>
> 关键点：如果残留数据 L ≥ 56，那么 `1 + L + 8 > 64`，一个块放不下，必须补**两个**块（128 字节）。

### Q6: 你提到修了一个哈希 bug，具体是什么？

> **现象**：空字符串哈希正确，任何非空输入都错。
>
> **排查**：
> 1. 空串通过、`"abc"` 失败 → 问题与「有残留数据」有关；
> 2. 写逐字节 update 测试，1 字节失败、0 字节通过 → 锁定残留缓冲区逻辑；
> 3. 看 `digest()`：它构造 `padding` 数组，**先把 `buffer` 的残留 set 进去**，再补 `0x80` 和长度，然后调 `consume(padding)`。
>
> **根因**：`consume()` 第一步是「把 `buffer` 的残留拼到 `chunk` 前面」。此时 `bufferLength` 还是 L，残留被拼了**两次**：
> ```
> 期望： [数据L][0x80][0x00...][长度]
> 实际： [数据L][数据L][0x80][0x00...]
> ```
> 空输入时 `bufferLength === 0`，`padding.set(buffer.subarray(0,0))` 什么也没做，补齐分支也被跳过，恰好正确。这解释了「为什么只有空串对」。
>
> **修复**：`this.bufferLength = 0` 之后再 `consume(padding)`。
>
> **防回归**：加了 3 条专门测试（55/56/单字节），并与 Node `crypto` 做全尺寸交叉验证。

### Q7: `crypto.subtle.digest` 为什么不能用？它不是很慢吗？

> 不是因为慢，是因为**内存**。签名是 `digest(algorithm, data)`，`data` 必须是完整的 `ArrayBuffer`。10GB 文件要先 `await file.arrayBuffer()` 读进内存——直接 OOM。
>
> 它本身很快（原生实现 + 可能用 CPU 指令集加速）。**小文件（<100MB）我完全推荐用它**，代码短、性能好、无 bug 风险。
>
> 我的实现是在「必须支持 GB 级 + 内存恒定」约束下的选择。

### Q8: 为什么把哈希放 Worker？主线程会怎样？

> 哈希是**纯 CPU 密集**操作，没有 IO 等待。主线程跑 2GB 文件，页面会**完全冻结**：
> - 进度条不刷新（渲染被阻塞）；
> - 按钮点不动（事件排队）；
> - 用户以为卡死，直接关页面。
>
> 放 Worker 后主线程全程可交互，每 4MB `postMessage` 一次进度。
>
> **细节**：`postMessage({ file })` 不复制文件内容。`File` 是 `Blob` 的子类，结构化克隆按引用传递（共享文件句柄）。

### Q9: Worker 里为什么要 `setTimeout(0)` 让出？

> Worker 内部也是一个事件循环。如果 `while` 循环里连续执行（`await arrayBuffer()` 虽异步，但 microtask 可能连续跑），Worker 就没机会处理新消息。
>
> 用户点「暂停」时主线程会 `worker.terminate()`，如果 Worker 卡在同步循环里，terminate 要等循环结束。`setTimeout(0)` 是 **macrotask**，强制让出，让消息队列能插进来。
>

## C. 分片与并发

### Q10: 分片大小怎么定的？5MB 有什么依据？

> 三个约束的平衡：
>
> | 约束 | 倾向小分片 | 倾向大分片 |
> |---|---|---|
> | 请求数量 | ✗ 1MB 分片，2GB = 2048 个请求 | ✓ 5MB = 400 个请求 |
> | 断点粒度 | ✓ 失败只重传 1MB | ✗ 重传 5MB |
> | 单请求超时风险 | ✓ 小 | ✗ 大 |
> | 服务端内存 | ✓ 小 | ✗ 大（`express.raw` 要缓冲整个分片） |
>
> 5MB 是常见默认值（阿里云 OSS 也是 5MB 起步）。页面提供 1/5/10/20/50MB 可选——**弱网用小分片，内网用大分片**。

### Q11: 并发数为什么默认 3？不是越高越快吗？

> 不是。受两个限制：
> 1. **浏览器连接数限制**：HTTP/1.1 下同域名最多 **6 个**并发连接。设 10 也只会有 6 个在跑，剩下排队，反而增加调度开销；
> 2. **服务端承受力**：每个分片是 `express.raw` 请求，会在内存里缓冲整个分片（最大 64MB）。6 并发 × 50MB = 300MB 峰值。
>
> 留 3 个连接给其他请求（比如列表刷新），所以默认 3。
>
> **优化方向**：HTTP/2 下同域复用一条连接，可以更高；更好的做法是**根据 RTT 和丢包自适应**（类似 TCP 拥塞控制），当前没做。

### Q12: 你的并发池怎么实现的？会有竞态吗？

> **共享游标 + 多个 worker**：
> ```ts
> let cursor = 0
> const worker = async () => {
>   while (runtime.running && cursor < pending.length) {
>     const index = pending[cursor]
>     cursor += 1              // 同步自增
>     await uploadChunk(index) // 异步上传
>   }
> }
> await Promise.all(Array.from({ length: 3 }, () => worker()))
> ```
>
> **不会竞态**：`pending[cursor]` 读取和 `cursor += 1` 之间**没有 `await`**，JS 单线程保证这段原子。
>
> 换成 Go / Java 就不行：`cursor++` 是「读-改-写」三步，多线程会丢更新，必须用 `AtomicInteger.getAndIncrement()` 或加锁。这是 JS 单线程模型省掉的东西。
>
> 我写了测试：20 个分片并发上传，断言 **`new Set(索引).size === 20`**，确保没有重复。

### Q13: 如果用 Promise.all 一次发所有分片会怎样？

> 三个问题：
> 1. **浏览器限制**：只会同时跑 6 个，剩下排队，但**内存里会同时存在 400 个 FormData**（5MB × 400 = 2GB）；
> 2. **无法控制进度**：全部发出后，失败时无法决定要不要继续发剩余的；
> 3. **暂停困难**：要维护 400 个 AbortController。
>
> 并发池把「同时存在的请求数」限制在 3 个，内存和可控性都好。

## D. 断点续传

### Q14: 断点续传的实现原理？

> 断点信息存在**两个地方**：
>
> | 位置 | 内容 | 作用 |
> |---|---|---|
> | 服务端 `uploads/chunks/<hash>/<index>` | 实际落盘的分片 | 以磁盘为准，换浏览器/清缓存/服务重启都能续 |
> | 浏览器 `localStorage` | `{fileKey, fileHash, uploadedChunks}` | 服务端不可用时兜底；缓存 fileHash 避免重算 |
>
> 续传流程：
> 1. 前端 `POST /check` 带 fileHash；
> 2. 服务端返回磁盘上已有分片 `[0,1,2,5]`；
> 3. 前端与本地记录**取并集**；
> 4. 只上传剩余的 `{3,4,6,7,...}`。

### Q15: 为什么取并集，而不是直接用服务端的？

> 因为两边都可能比对方新：
> - **本地更全**：刚传完第 3 片、写入了 localStorage，但 `check` 还没发出（或服务端刚好挂了）；
> - **服务端更全**：用户换了浏览器，新环境 localStorage 是空的。
>
> **这个 bug 是写单测时发现的**——注释写着「合并本地记录与服务端分片」，但实现只合并了服务端。测试用例「本地有 [0]，服务端有 [1]，应该只传 [2,3,4]」直接暴露了它。

### Q16: 刷新页面后为什么必须重新选文件？

> 浏览器安全限制：页面无法通过路径重新获得 `File` 对象，`File` 只能来自用户主动操作。
>
> 当前实现：刷新后从 localStorage 恢复出「已暂停」的占位卡片，用户重新选择同一文件，校验 **name + size 一致**后继续，此时复用缓存的 fileHash，**跳过哈希计算**。
>
> **为什么只校验 name + size**：此时还没算哈希。名 + 大小能过滤 99% 误选，剩余风险由服务端兜底——内容真变了，`check` 返回的分片对不上，最终合并会因大小校验失败。
>
> **更好的方案**（Chrome 专属）：用 `showOpenFilePicker()` 拿到 `FileSystemFileHandle`，这个对象**可以存进 IndexedDB**，刷新后取出仍能读文件，能做到真正的全自动续传。

### Q17: 分片上传到一半，服务端崩了会怎样？

> 分片是**逐片落盘**的（`fs.writeFile`），已写入的不丢。服务重启后：
> 1. `uploadStates` 内存缓存清空；
> 2. 下次 `/check` 调 `readReceivedChunks()` **读磁盘目录**，恢复出已上传列表。
>
> 这就是注释写「以磁盘为准，服务端重启也能续传」的原因。

## E. 服务端合并

### Q18: 合并分片的实现？为什么用 pipeline？

> ```ts
> const out = createWriteStream(tmpPath)
> for (let i = 0; i < totalChunks; i++) {
>   await pipeline(createReadStream(chunkFile(hash, i)), out, { end: false })
> }
> await new Promise((r) => out.end(r))
> await fs.rename(tmpPath, target)
> ```
>
> **为什么不用手写 `pipe`**：
> ```ts
> // ❌ 有死锁风险的写法
> src.pipe(out, { end: false })
> await new Promise((r) => out.once('drain', r))
> ```
> 如果 `pipe` 内部已经把数据全写完了（没触发 drain），`once('drain')` 就永远等不到 → **死锁**。这种时序竞争极难复现但线上会遇到。
> `pipeline` 内部正确处理了背压、错误传播、资源清理。
>
> **`{ end: false }`**：默认 `pipeline` 在源结束时关闭目标流。多个分片共用一个 `out`，第一个就把流关了后面全失败。

### Q19: 为什么写临时文件再 rename？

> `fs.rename` 在同一文件系统上是**原子操作**。
>
> 如果直接写最终路径：用户在合并进行中（比如第 7/10 片时触发合并）下载，会拿到「只有 70% 内容」但文件名完全正常的文件，用户不会察觉，数据就损坏了。
>
> 临时文件 + rename 保证：最终路径上**要么没有文件，要么是完整文件**。

### Q20: 合并后怎么保证文件没坏？

> 合并完对比 `stat.size` 和 `state.fileSize`，不一致就报错并保留分片目录。
>
> **但这是弱校验**：只验证长度。如果某个分片被截断、另一个重复，总长度可能恰好对上。
>
> **更强的做法**（当前没做）：合并完再算一次 SHA-256，与前端传来的 `fileHash` 对比。这是端到端校验，能 100% 保证内容正确。代价是要多读一遍整个文件。
>
> 折中：只对前 N 片和最后 1 片做抽样校验。

### Q21: GB 级文件合并要多久？怎么优化？

> 串行读取 + 写入，受磁盘 IO 限制，约 200~500MB/s。10GB 需要 20~50 秒，这期间用户看到「合并中」。
>
> 优化方向：
> 1. **预分配 + 并行写**：`fs.write(fd, buffer, 0, len, position)` 支持指定写入位置，可以开 4~8 个并发各负责不同区间，理论能跑满 SSD 带宽；
> 2. **`copy_file_range`**：Linux 内核的零拷贝区间复制，Node 的 `fs.copyFile` 不暴露这个能力；
> 3. **别合并**：把分片直接当对象存储的 Multipart 数据，让存储层处理。
>
> 当前选了「简单 + 正确」，性能优化列为 TODO。

## F. 安全

### Q22: 秒传有没有安全风险？

> 有，而且是**经典秒传漏洞**。如果只按 fileHash 判断「文件是否存在」，攻击者可以：
> 1. 上传文件拿到 hash；
> 2. 删掉自己这边的记录（服务端文件还在）；
> 3. 用 hash 秒传——其实什么都没传，但列表里出现了文件。
>
> 更严重的是**跨用户**问题：如果秒传全局共享，A 上传了机密文件，B 只要知道 hash 就能秒传得到一份完整的。
>
> **我的实现**：`findMetaOfUser(fileHash, ownerId)` —— **按 ownerId 隔离**，只有自己的文件才能秒传命中，跨用户秒传不存在。
>
> **代价**：不同用户上传同一文件会各存一份，浪费磁盘。生产级应该用**引用计数**：磁盘只存一份，`files.json` 里多条记录指向同一物理文件，删除时引用减一。

### Q23: 你提到的「分片目录归属校验」是什么漏洞？

> 分片目录以 `fileHash` 命名，而 hash = 内容摘要，是**可预测/可泄漏的**（比如用户分享了文件，hash 就暴露了）。
>
> 不校验归属时有两个攻击面：
>
> **攻击 A：污染**
> ```
> 攻击者 → POST /upload/chunk { fileHash: 受害者的hash, index: 99, file: 伪造内容 }
> → 分片被写进受害者的分片目录
> → 受害者传完触发合并 → 得到被污染的文件
> ```
>
> **攻击 B：窃取半成品**
> ```
> 受害者传完 9/10 片后中断
> 攻击者 → POST /upload/merge { fileHash: 受害者的hash }
> → 无校验的话，攻击者白白拿到一个完整文件
> ```
>
> **修复**：独立的 `chunk-owners.json` 记录 `{hash: ownerId}`。目录首次使用时由第一个访问者认领，后续只允许原归属者操作，否则 403。`/check`、`/chunk`、`/merge` 三个入口都校验。
>
> **为什么单独一个文件**：塞进 `files.json` 的话每次校验都要遍历整个列表 O(n)；独立文件是 O(1) 查表。

### Q24: 文件路径穿越怎么防？

> 两处：
> 1. **文件名**：`path.basename()` 去掉路径部分，再替换 `\/:*?"<>|` 等危险字符，截断到 180 字符；
> 2. **hash**：`/^[a-zA-Z0-9_-]{16,128}$/` 白名单正则，不合法直接 400。hash 会直接拼进目录路径，不校验的话 `fileHash = "../../etc"` 就能写到任意位置。
>
> 原则：**凡是拼进文件路径的用户输入，必须白名单校验**，而不是黑名单过滤 `../`。

## G. 下载与 Range

### Q25: 下载为什么要用 fetch 而不是 `<a download>`？

> `<a>` 标签**无法携带自定义请求头**，而下载接口需要 `Authorization: Bearer xxx`。
>
> 方案对比：
>
> | 方案 | 能带 token | 能显示进度 | 大文件内存 |
> |---|---|---|---|
> | `<a download>` | ✗ | ✗ | 浏览器优化 |
> | `window.open` | ✗ | ✗ | 浏览器优化 |
> | token 放 URL query | ✓（会泄漏到日志） | ✗ | 浏览器优化 |
> | `fetch` + `getReader()` | ✓ | ✓ | 可控 |
>
> `fetch` 的 `response.body` 是 `ReadableStream`，可以边读边处理。

### Q26: 下载怎么避免占用内存？

> 三级方案：
> 1. **File System Access API**（Chrome/Edge）：`showSaveFilePicker()` 拿句柄，`createWritable()` 后边读边写盘。内存恒定，GB 级没问题；
> 2. **Blob 回退**（Firefox/Safari）：分块读进数组，最后拼 `Blob`。内存 = 文件大小，2GB 可能失败；
> 3. **不支持 stream**：报错提示。
>
> **Firefox 的改进方案**：Service Worker 拦截请求做代理，把流式响应「伪装」成普通下载；或服务端提供分片下载接口，前端逐片下载后用 StreamSaver 拼流。
>
> **用户取消的区别**：另存为对话框点取消抛的是 `DOMException: AbortError`，要单独判断并直接结束，**不能走 Blob 回退**——否则用户点了取消却弹出下载，很困惑。

### Q27: HTTP Range 你支持哪些形式？

> 遵循 RFC 7233，只处理单段：
>
> | 请求 | 结果 |
> |---|---|
> | `bytes=0-99` | 206，`Content-Range: bytes 0-99/1000` |
> | `bytes=900-` | 206，900 到末尾 |
> | `bytes=-100` | 206，最后 100 字节（suffix range） |
> | `bytes=900-99999` | 206，end **截断**到 999，不报错 |
> | `bytes=1000-1099` | **416** + `Content-Range: bytes */1000` |
> | `bytes=500-100` | **416**（start > end） |
> | `bytes=0-99,200-299` | 忽略，返回 200 全量 |
>
> **为什么 end 越界要截断而不是报错**：RFC 明确规定。客户端常用 `bytes=0-` 或传一个大 end 来「取剩下的全部」，报错会让断点续传工具全部失效。
>
> **为什么 start 越界返回 416**：让客户端明确知道「这个范围不存在」，可据此判断文件是否被替换/缩小。
>
> **为什么不支持多段**：`multipart/byteranges` 要生成 boundary、拼接多段头，实现复杂；浏览器和下载工具几乎只用单段。RFC 允许忽略 Range 返回全量。
>
> 我把这段抽成了纯函数 `range.ts`，写了 **15 个单元测试**覆盖所有边界。

### Q28: `Content-Disposition` 中文文件名怎么处理？

> ```ts
> const encoded = encodeURIComponent(fileName)
> const ascii = fileName.replace(/[^\x20-\x7e]/g, '_')
> res.setHeader('Content-Disposition',
>   `attachment; filename="${ascii}"; filename*=UTF-8''${encoded}`)
> ```
>
> HTTP 头只能是 ASCII。RFC 5987 定义了 `filename*=UTF-8''<percent-encoded>` 语法来表达非 ASCII 文件名。
>
> **两个都给的原因**：
> - 老客户端只认 `filename=`，给个 `_____abc.pdf` 总比乱码好；
> - 现代浏览器优先用 `filename*=`，拿到正确的中文名。

## H. 工程化

### Q29: 你的测试覆盖了什么？怎么保证哈希正确？

> 前端 60 个 + 后端 15 个 = 75 个用例。
>
> **哈希正确性**三层验证：
> 1. **NIST 官方测试向量**（4 条）：不依赖环境，证明算法本身正确；
> 2. **与 Node `crypto.createHash` 交叉验证**：18 种尺寸 × 随机数据；
> 3. **分片方式无关性**：同一份数据用 1/3/7/63/64/65/1024/4096/65536 字节切分，结果必须一致。
>
> **尺寸不是随机选的**，每个对应一段代码分支：55/56 是 padding 分界点，64/65 是整块分界点，63 是「差 1 字节满块」。
>
> **回归测试以 bug 命名**（`padding 重复消费的 bug`），让后来的人知道这段代码为什么长这样。
>
> **还没做的**：集成测试（真实起服务 + 真实写盘）和 E2E（Playwright）。当前只覆盖纯逻辑层。

### Q30: 这个模块如果上生产，你还缺什么？

> 按优先级：
>
> | 优先级 | 缺口 | 说明 |
> |---|---|---|
> | P0 | **元数据并发写** | `files.json` 是内存数组 + 全量覆写，两个请求同时写会丢数据。要换 SQLite 或加写锁 |
> | P0 | **文件内容端到端校验** | 合并后只校验长度，应该再算一次 SHA-256 对比 |
> | P1 | **引用计数** | 不同用户上传同一文件各存一份，浪费磁盘 |
> | P1 | **分片直传对象存储** | 分片流量不经过应用服务器，用预签名 URL |
> | P1 | **磁盘容量保护** | 当前没有总容量上限，用户可以写满磁盘 |
> | P2 | **模糊测试** | 对 `parseMultipart` 的畸形输入做 fuzz |
> | P2 | **服务端监控埋点** | 前端有耗时日志，服务端缺 |
>
> **我最担心的是 P0 的元数据并发写**——单机小流量没问题，但这是真实的数据丢失风险。

## 附：现场白板题

如果面试官说「画一下这个流程」，按这个顺序画：

```
1. 画三个框：浏览器 / Worker / 服务端
2. 浏览器 → Worker：传 File 引用
3. Worker 循环：slice → update → postMessage(progress)
4. Worker → 浏览器：hash
5. 浏览器 → 服务端：POST /check
6. 服务端 → 浏览器：exists? / uploadedChunks
7. 分叉：
   - exists=true → 秒传，直接完成
   - exists=false → 画 3 条并发线，标 cursor 共享
8. 每片完成 → localStorage 打勾
9. 最后一片 → 服务端合并（临时文件 + rename）
10. 服务端 → 浏览器：url
```

**加分动作**：在第 7 步旁边标注「取并集」、在第 9 步旁边标注「原子替换」——面试官会知道你想到了边界情况。
