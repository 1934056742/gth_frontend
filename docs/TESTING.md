# 测试说明

分两端：前端用 **Vitest**（116 个用例），后端用 **Node 内置 `node:test`**（51 个用例），
合计 167 个用例。绝大部分是纯逻辑单测，不需要启动数据库或真实服务，秒级跑完
（`ai.test.ts` 与 `ai.ts` 的用例会在进程内起一个临时 HTTP 服务，同样不依赖外网）。

```bash
# 前端
cd frontend
npm test              # 跑一次
npm run test:watch    # 监听模式
npm run test:coverage # 覆盖率

# 后端
cd backend
npm test
```

## 一、前端：`src/utils/sha256.test.ts`（37 个用例）

被测对象：`src/utils/sha256.ts`（增量 SHA-256）

### 1. 标准测试向量（5 个）

用 NIST / RFC 6234 官方值，**不依赖任何环境**，任何人跑都能验证：

| 输入 | 期望摘要（前 12 位） |
|---|---|
| `""` | `e3b0c44298fc...` |
| `"abc"` | `ba7816bf8f01...` |
| `"abcdbcdecdefdefg..."`（56 字节） | `248d6a61d206...` |
| `"abcdefghbcdefghi..."`（112 字节） | `cf5b16a778af...` |
| 512KB 的 `'a'` | 与 Node `createHash` 一致 |

> 为什么要有这组：如果只和 Node 对比，Node 的 API 变了或者测试环境特殊，就验证不了算法本身对不对。

### 2. 与 Node `crypto` 交叉验证（18 个）

**关键尺寸覆盖**（`sizes` 数组）：
```
0, 1, 2, 3, 54, 55, 56, 57, 63, 64, 65, 127, 128, 129, 1000, 4096, 65537, 1000003
```

这些尺寸不是随便选的，每个都对应一段代码分支：

| 尺寸 | 覆盖的分支 |
|---|---|
| 0 | 空输入，`bufferLength === 0` |
| 1~3 | 残留 < 64，`consume` 的"暂存"分支 |
| 54 / 55 | padding 只需 1 个块（`bufferLength < 56`） |
| **56** | padding 需要 **2 个块**的临界点（`bufferLength >= 56` → 128 字节） |
| 57 / 63 | 需要 2 个块的区间 |
| 64 / 65 | 恰好一个整块 / 一个整块 + 1 字节 |
| 127 / 128 / 129 | 多个整块 + 各种残留 |
| 65537 | 跨越多块，且是质数避免巧合 |
| 1000003 | 大输入，验证长时间累积不出溢出 |

**分片方式无关性**（`chunkSizes` 数组）：`1, 3, 7, 63, 64, 65, 1024, 4096, 65536`

同一份 200KB 数据，用不同尺寸切分后逐块 `update`，结果必须与一次性摘要完全一致。
这验证的是 `update()` 可被**任意次、任意长度**调用——这是流式哈希最核心的契约。

还包含：
- **逐字节 `update`**（最极端情况，1000 次调用）

### 3. 回归测试：padding 重复消费 bug（3 个）

这个 bug 是实际踩到的：

```ts
// 错误写法
const padding = new Uint8Array(padLength)
padding.set(this.buffer.subarray(0, this.bufferLength), 0)  // 已含残留数据
padding[this.bufferLength] = 0x80
// ... 这里忘了 this.bufferLength = 0
this.consume(padding)   // consume 又把残留数据拼了一次 → 数据重复
```

结果：**所有非空输入全错，只有空输入恰好正确**（因为 `bufferLength === 0` 时那行 `padding.set` 什么也没做）。

这三条用例锁死：55 字节、56 字节、单字节输入。

### 4. `toHex`（1 个）
小写输出、两位补齐（`0 → "00"`，`255 → "ff"`）。

## 二、前端：`src/utils/uploadManager.test.ts`（26 个用例）

被测对象：`src/utils/uploadManager.ts`（上传调度引擎）

**测试环境：** `jsdom`（需要 `localStorage` 和 `File` / `FormData` / `DOMException`）

**Mock 策略：** 只 mock 边界（API 层和哈希计算），中间逻辑全部真实执行。

```ts
vi.mock('@/api/upload', () => ({ checkFile, uploadChunk, getFiles }))
vi.mock('@/utils/hash', () => ({ calculateFileHash, /* buildFileKey 保留真实实现 */ }))
```

### 1. 格式化工具（3 个）
`formatSize` / `formatSpeed` / `formatRemaining` 的边界（0、无穷、三级时间单位）。

### 2. 分片切分（4 个）

| 用例 | 验证点 |
|---|---|
| 100 字节 / 10 字节片 | 片数 = 10 |
| 105 字节 / 10 字节片 | 片数 = 11（向上取整） |
| 0 字节文件 | 至少 1 片（避免除零） |
| 105 字节切片 | 10 片 × 10 字节 + 1 片 × 5 字节，**总字节数 = 105**（不越界、不丢字节） |

最后一条最重要：`file.slice(start, end)` 的 `end` 计算错了就会多读或漏读。

### 3. 秒传（2 个）
- `check` 返回 `exists: true` → 任务直接 `done`、`instant = true`、**一个分片请求都不发**、localStorage 不残留记录；
- 每个任务只调用一次 `calculateFileHash`。

### 4. 断点续传（4 个）

| 用例 | 验证点 |
|---|---|
| 服务端已有 `[0,1]` | 只上传 `[2,3,4]` |
| 本地记录有 `[0]` + 服务端有 `[1]` | 只上传 `[2,3,4]`（**取并集**，这个用例抓出了真实 bug） |
| 上传中途 | localStorage 已有第 0 片；全部完成后记录被清除 |
| `check` 接口报错 | 按本地记录继续，不阻塞上传 |

第二个用例的价值：代码注释写着"合并本地记录与服务端分片"，但原实现**只合并了服务端**。写完这个测试才发现。

### 5. 分片重试（3 个）

| 用例 | 验证点 |
|---|---|
| 前 2 次失败，第 3 次成功 | 总调用 3 次，任务最终 `done` |
| 401 鉴权错误 | **只调用 1 次**，直接 `error`（重试没意义） |
| 一直失败 | 调用 3 次后 `error`（不超过最大重试次数） |

### 6. 并发控制（3 个）

| 用例 | 验证点 |
|---|---|
| 设为 2 并发上传 12 片 | 统计同时在途数，**峰值 ≤ 2**，且 12 片全部上传 |
| 20 片并发上传 | 每个 index **只出现一次**（游标不重复） |
| `setMaxConcurrency(100)` | 被钳制到 6；`0` → 1 |

### 7. 任务管理（4 个）
- 同一文件重复添加 → 去重，第二次返回空数组；
- `pauseTask` 后不再发起新分片，状态变 `paused`；
- `removeTask` 从队列移除；
- `clearFinished` 只清 `done` 的任务。

## 四、前端：其余模块（共 53 个用例）

| 文件 | 用例数 | 覆盖内容 |
|---|---|---|
| `src/utils/permission.test.ts` | 23 | 角色解析、路由访问判断、菜单按角色生成、路由守卫拦截 |
| `src/api/ai.test.ts` | 11 | SSE 事件切分 / 解析、增量拼接、异常与中断处理 |
| `src/utils/typewriter.test.ts` | 10 | 打字机缓冲：按帧吐出、不丢字、积压自动加速、结束冲刺、`flush` / `stop` |
| `src/utils/markdown.test.ts` | 9 | Markdown 渲染、HTML 转义防注入、流式未闭合语法补全 |

**`typewriter.test.ts` 为什么单独存在**：AI 回答的流式粒度是每块 1~2 个字、
吐字速度可达 300+ 字/秒，直接渲染会出现「先冒出几个字 → 卡住 → 一下子全出来」。
打字机缓冲把它转成平稳输出，这类时间相关的逻辑用 `vi.useFakeTimers()` 才能稳定断言：

| 用例 | 验证点 |
|---|---|
| 增量不会立刻全部展示 | `push` 后不经过定时器，展示文本仍为空 |
| 内容最终会完整吐出 | 多块拼起来与原始文本完全一致，不丢字 |
| 积压变多会自动加速 | 单帧吐出量 > 基础值，保证不越落越远 |
| `finish()` 冲刺排空 | 结束后几帧内刷完并触发一次 `onDrain` |
| `flush()`（用户点停止） | 立即吐出全部剩余内容 |
| `stop()` | 之后不再更新界面（防卸载后定时器回调） |
| 中文 / emoji | 不被截断成乱码 |


## 五、还缺什么（诚实说明）

当前是**单元测试**，还有两块没覆盖：

### 1. 集成测试（建议补）
需要真实起服务 + 真实写盘，验证：
- 多分片真实落盘 → 合并 → 文件字节完全一致；
- 归属校验返回 403；
- 清理任务真的删掉了过期目录。

> 这部分之前用一次性脚本手动验证过（25MB 文件 / 5 分片 → 合并 → 下载 → 逐字节比对通过），但没有沉淀成可重复执行的测试。

### 2. E2E 测试（建议补）
Playwright 驱动真实浏览器：
- 选几百 MB 文件 → 进度条平滑、页面不冻结；
- 上传到一半刷新 → 续传；
- 下载时取消 → 无报错。

### 3. 覆盖率
`npm run test:coverage` 需要先装 `@vitest/coverage-v8`：

```bash
npm i -D @vitest/coverage-v8
```

## 六、为什么这么测（面试可讲）

**「测试不是覆盖率数字，是设计约束」**

- **标准向量 + 交叉验证并存**：向量保证"离开这台机器也对"，交叉验证保证"大批随机数据也对"。
- **边界尺寸是照着代码分支选的**：55/56 不是随机数，是 padding 逻辑的分水岭。这说明测试者**读过实现**。
- **并发池测"峰值"而不是"最终结果"**：最终结果对了但并发失控，一样是 bug。要能观测过程。
- **401 单独测**：区分"该重试的错误"和"不该重试的错误"，体现对重试语义的理解。
- **回归用例以 bug 命名**：`padding 重复消费的 bug` —— 让后来的人知道这段代码为什么长这样。
